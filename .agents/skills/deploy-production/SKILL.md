# Production deployment

This is a live Gmail-connected Worker with a five-minute cron. A deployment can replace Worker code, dashboard assets, configuration variables, routes, and cron schedules; it does not reset the persistent processing mode in D1. Follow `docs/DEPLOY.md` (especially sections 5–9) and `docs/OPERATIONS.md` for the current runbook. This skill is a guardrail for agents, not permission to deploy: only execute it when the user explicitly asks for a production deployment.

## Identify the release and target

1. Inspect `git status --short`, the intended changes, `package.json`, and `wrangler.jsonc`. Establish what the current working tree will ship, including uncommitted files and generated assets. Do not discard or silently include unrelated user changes. If the requested release cannot be distinguished from unrelated changes that affect the bundle, resolve that ambiguity before deploying.
2. Confirm the intended target is `env.production` in `wrangler.jsonc`: Worker `email-triage-badi`, its production D1 binding, custom domain `email-triage.tellbadi.com`, and configured cron. Use the project's Bun/Wrangler versions (`bun install --frozen-lockfile` if dependencies are missing); check `bunx wrangler whoami` against the configured account. Do not substitute a default-environment deploy.
3. Before mutation, record the current deployment and operational baseline: `bunx wrangler deployments list --env production`, public `/healthz`, and authenticated `GET https://email-triage.tellbadi.com/api/v1/status`. Inspect at least `mode`, `authStatus`, sync/backlog/error indicators, `aiBudget`, and label readiness. Get the admin token through an existing secure channel; never print it, commit it, or assume `.dev.vars` is the production credential. If the authenticated baseline or target account cannot be established, stop rather than guessing whether production is in `apply` mode.

## Preflight and migrate

4. Run `bun run format:check`, `bun run lint`, `bun run typecheck`, `bun run test`, and `bun run build`. The last command packages the **default** environment, not production: also run `bun run web:build` followed by `bunx wrangler deploy --env production --dry-run` to validate the intended bundle and assets. Do not deploy if a relevant check fails; investigate and fix the cause. `bun run test` may create a placeholder `web/dist/index.html`, so always build real dashboard assets again before the deploy.
5. Check pending migrations with `bunx wrangler d1 migrations list email-triage-badi --remote --env production` for every release; the list shows **unapplied** files. If the release changes `src/db/schema.ts` or `migrations/`, review the committed generated SQL and its compatibility with running code. A pending `0000_initial.sql` against an existing populated database is a stop condition, not a reason to reapply the baseline. For destructive or non-backward-compatible changes, arrange a verified backup and safe staged rollout instead of automatically applying them. Apply reviewed, compatible pending migrations **before** dependent code with `bunx wrangler d1 migrations apply email-triage-badi --remote --env production`; inspect the result. Never regenerate or rewrite migration history on a deployed database.
6. Review changes to `wrangler.jsonc` separately: production `vars` can be replaced by the values in config on deploy; `DEFAULT_MODE` only initializes state and does not override D1 mode. Check the production account, bindings, schedule, routes, model/rubric, budget, and flags against intended behavior. Secrets are not part of routine deployment; do not rotate or publish secrets, change persistent mode, trigger processing, or enable the optional GitHub fast path merely to ship code. Secret changes are separate live operations and need explicit scope.

## Release and verify

7. Run `bun run deploy` only after preflight and any prerequisite migrations pass. It rebuilds `web/dist` and deploys with `wrangler deploy --env production`; plain `wrangler deploy` and `bun run build` do **not** release the intended production configuration. Capture Wrangler's deployed version/output; a successful command alone does not prove the app works.
8. Recheck `/healthz` and dashboard HTML/assets at the production domain, then authenticated `/api/v1/status`. Compare persisted `mode`, Gmail auth/owner state, backlog/error indicators, AI budget and label readiness with the baseline; observe the next scheduled tick or logs if the change affects processing. A 200 from `/healthz` is only liveness. Do not run a manual tick, live evaluation, backfill, reprocessing, or mode switch as a smoke test: those can spend AI budget or mutate Gmail. If a relevant runtime path must be exercised, choose a bounded read-only check or obtain explicit scope for the live action.
9. If verification fails, stop further mutation, report the actual state, and use `docs/OPERATIONS.md#6-recovery-procedures`. A Worker rollback does not undo D1 migrations or Gmail label changes; check the previous version's schema compatibility before rollback. Do not automatically revert database state or user mail. Report the deployed version, target, checks, migrations applied (or none), before/after mode and health/status, and any remaining risk or blocker. Never claim production is healthy from a dry-run alone.
